## 2. Entscheidung zum Prettier-Geltungsbereich

Gewählt wurde **Variante (a): `prettier --write` für alle 37 Dateien**, also volle Formatierung
inklusive Produkt-HTML/CSS/JS, statt Ausnahmen in `.prettierignore`.

Begründung:

- Die Codebasis ist CommonJS/ESM ohne Build-Transpiler; Prettier-Formatierung von JS ist
  nachweislich semantikneutral (AST-Vergleich, Abschnitt 4).
- Ein `.prettierignore`-Scope hätte genau die Dateien ausgenommen, in denen der Lint-Job
  künftig Regressionen finden soll (Produkt-CSS/HTML/Module). Das Gate wäre grün, aber schwach.
- Das Rendering-Risiko ist messbar statt plausibel: 48 Screenshots in beiden Zuständen sind
  byte-identisch (Abschnitt 4). Damit ist die Massenreformatierung belegt unschädlich.
- `.prettierignore` und `.prettierrc.json` wurden **nicht** verändert (byte-identisch zum

### 3.1 Dabei gefundene, stille Build-Regression (Ursache, nicht Symptom)

Prettier serialisiert Void-Elemente als `<link … />` und bricht lange Attributlisten um. Der
Offline-Build `scripts/build-local.cjs` erkannte Stylesheets aber nur über das exakte Literal
`<link rel="stylesheet" href="css/x.css">`. Nach der Formatierung matchte das nicht mehr:

- Folge: das CSS wurde im `Lokal.html` **nicht mehr inline eingebettet**, stattdessen blieb ein
  externer `<link rel="stylesheet">` stehen — der Offline-Einzeldatei-Build wäre still kaputt
  gewesen (keine Fehlermeldung; die Offline-Tests hätten es wegen des zweiten Fehlers unten
  nicht zwingend bemerkt).
- Nachweis vor dem Fix: `Lokal.html: CSS inlined (style[data-source]): 0`,
  `no external stylesheet <link>: FAIL` (Zwischenstand, in der Konversation belegt).

Behoben in `scripts/build-local.cjs`, ohne die Ausgabeabsicht zu ändern: die Ersetzungen für
Stylesheet-Inlining, Favicon-Data-URL, Modul-`<script>` und den `<html lang="de">`-Banner sind
jetzt attributreihenfolge- und umbruchtolerant (Regex über das ganze Tag, `href` separat
extrahiert, `css/`-Präfix bleibt Pflicht, der `@import|url()`-Guard bleibt erhalten).
Nachkontrolle: `Lokal.html: CSS inlined (style[data-source]): 2`, keine externen Stylesheets,
keine Modul-Skripte, keine Font-Links, Favicon und Kristalldaten inline.

### 3.2 Eine Assertion an die Formatierung angepasst (kein Test entfernt)

`tests/pages-regression.cjs` prüfte `<base href="/Esoterik-Welt/">` als exaktes Literal. Prettier
schreibt `<base href="/Esoterik-Welt/" />`, wodurch 3 von 6 Tests rot wurden. Die Assertion prüft
jetzt `/<base href="\/Esoterik-Welt\/"\s*\/?>/` — gleiche Absicht (Base-Ziel muss das
Pages-Projekt sein, nicht `/` und nicht extern), tolerant nur gegenüber dem Leerzeichen/Slash.
Kein Test gelöscht, keiner übersprungen (`grep` auf `.skip`/`.todo` in `tests/` und `scripts/`
liefert nichts), `npm test`/`test:pages`/`test:offline`/`test:e2e` zählen unverändert 2/6/2/56.

### 3.3 Nebenfund und -fix: `npm run build:local` war ein No-Op

`scripts/build-local.cjs` exportierte nur `buildLocal()` und rief sich nie selbst auf;
`npm run test:offline` (= `npm run build:local && node --test tests/offline-file.cjs`) hat damit
**kein** Artefakt gebaut, sondern irgendein vorhandenes `Lokal*.html` geprüft (auf einem frischen
Checkout: gar keins). Ergänzt wurde ein `require.main === module`-Einstieg mit Fehlerbehandlung.

identisch. Das ist Build-Tooling, kein Produktverhalten; die Änderung ist unabhängig revertierbar.
